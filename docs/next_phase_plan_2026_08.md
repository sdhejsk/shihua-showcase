# 海外油气数据展示与快速评价协同平台后续建设计划

## 1. 编制背景

目前，前期原型系统建设工作已经基本完成，系统已经能够接入并展示盆地、合同区块、油气田、井位、井资料、Excel 表格资料、PDF 文件目录和初步评价算法页面。项目已经从“能否做出一个演示系统”的阶段，进入到“如何继续建设成一个更接近业务使用的平台”的阶段。

根据 2026 年 7 月 31 日杭州会议纪要，以及后续沟通内容，下一阶段建设需要重点围绕以下方向推进：

- 对标首席提供的旧平台“海外油气项目快速评价协同工作平台”，学习其界面风格、业务流程、功能组织方式和协同工作模式。
- 继续扩大数据接入范围，将现有标普数据、非洲区域数据以及后续可获得的海外油气资料逐步纳入平台。
- 从单纯的数据展示，逐步过渡到“数据管理 + 空间浏览 + 项目评价 + 方法库 + 任务协同 + 成果输出”的业务平台。
- 建立更加稳定、可观测、可维护的数据服务与数据库体系，解决目前数据量变大后加载慢、调试难、运行状态不透明的问题。
- 完善评价算法模块，使其从展示型页面升级为可输入参数、可选择方法、可输出结果和报告的快速评价工具。

## 2. 当前项目状态判断

### 2.1 当前已经达到的阶段

从当前系统完成度看，项目已经达到“原型验证 + 数据接入样机 + 区域闭环示范雏形”阶段。

具体来说，当前系统已经完成了以下工作：

- 建立了一个 Web 端数据展示平台原型。
- 接入了 MapGIS IGServer 作为 GIS 服务发布与访问平台。
- 发布并接入了井位、盆地、合同区块、油气田等 GIS 图层。
- 接入了部分 Excel 表格数据，并整理为前端可读取的数据结构。
- 实现了地图空间总览、图层开关、对象点击查看、属性卡片展示、数据目录、服务状态等功能。
- 初步完成了非洲区域数据闭环的尝试，包括非洲盆地、区块、油气田和井位等对象的空间展示。
- 搭建了评价算法模块雏形，但目前仍以演示和概念验证为主。

### 2.2 当前还没有达到的阶段

当前系统还不是一个正式的业务生产系统，也还没有完全达到会议纪要中“海外资源评价协同工作平台”的目标形态。

主要差距包括：

- 目前仍以文件和接口读取为主，尚未建立正式数据库管理体系。
- 数据接入流程仍偏手工化，缺少统一的数据入库、校验、版本管理和质量检查机制。
- 系统界面风格与旧平台、中石化内部系统风格仍存在差异。
- 评价算法模块还没有真正形成可配置、可输入、可计算、可解释、可复用的方法库。
- 项目登记、任务流转、负责人分工、评价状态、成果归档等协同功能还没有系统化实现。
- 大数据量地图加载、分页请求、缓存、性能监测和服务诊断能力还需要加强。
- 目前系统没有严格的权限体系、用户体系和项目级数据隔离机制。

## 3. 总体建设目标

下一阶段的总体目标，是把当前“数据展示型原型系统”升级为“海外油气项目快速评价协同平台”的初步业务版本。

目标平台应具备以下能力：

- 能统一管理海外油气项目相关的多源数据。
- 能按国家、区域、盆地、区块、油气田、井位等对象进行空间浏览和属性查询。
- 能围绕具体项目建立评价任务，记录负责人、评价年度、评价状态和工作进展。
- 能接入评价指标体系、标准规范值、评价方法和算法模型。
- 能支持典型评价流程，从基础数据查看到指标计算，再到评价结果输出。
- 能沉淀成果资料、过程资料、报告材料和后续项目档案。
- 能与旧平台功能逻辑保持一定一致性，便于向已有业务系统靠拢。

一句话概括：

下一阶段要把当前系统从“能展示数据的原型”，推进为“能支撑海外油气项目数据管理、空间分析、快速评价和协同流转的业务平台”。

## 4. 后续建设原则

### 4.1 对标旧平台，而不是简单复制旧平台

旧平台具备较强的业务参考价值，尤其是在项目登记、项目运行状况、待办任务、评价流程和方法库管理方面。但旧平台界面和技术形态较旧，不能完全照搬。

后续应采取“流程借鉴、功能吸收、界面优化、技术重建”的方式：

- 借鉴旧平台的业务模块和流程。
- 参考旧平台的数据表结构和评价材料组织方式。
- 不照搬旧平台老旧界面，而是形成更现代但仍符合业务习惯的平台风格。
- 如果能够获取旧平台源码和数据库结构，应重点用于理解业务逻辑，而不是直接依赖旧代码。

### 4.2 数据标准先行

会议纪要中明确提到，数据标准化是后续建设关键。当前已经暴露出国家名称、盆地名称、区块名称、字段命名、坐标参考系、服务名称等不统一问题。

后续需要优先建立：

- 国家编码标准。
- 盆地编码标准。
- 区块编码标准。
- 油气田编码标准。
- 井编码标准。
- 文件命名规则。
- GIS 坐标系和发布规则。
- Excel 表格字段映射规则。
- 数据更新和版本管理规则。

### 4.3 先做典型案例闭环，再做全量扩展

系统最终目标可以很大，但短期不宜一开始就追求全量数据和全功能。

建议先选择一个典型区域或典型盆地，完成一条完整业务闭环：

- 区域选择。
- 盆地查看。
- 区块查看。
- 油气田查看。
- 井位查看。
- 井资料查看。
- 评价参数输入。
- 评价算法计算。
- 评价结果展示。
- 报告导出。

该闭环跑通后，再扩展到更多区域和更多数据类型。

### 4.4 可观测、可调试、可解释

目前用户最担心的问题是系统运行像黑盒，尤其是数据量变大后，不知道请求是否成功、慢在哪里、MapGIS 是否承压、前端是否卡顿。

后续系统建设必须把“可观测性”作为基础能力：

- 每个数据服务请求都要能看到请求地址、耗时、返回数量、是否分页、是否失败。
- 前端要能显示当前图层加载状态。
- 后端要记录接口日志。
- MapGIS 服务要有监控和压力测试记录。
- 大数据量场景要有加载策略，而不是一次性把所有对象塞到浏览器。

## 5. 旧平台调研计划

### 5.1 旧平台需要重点调研的内容

首席提供的旧平台“海外油气项目快速评价协同工作平台”是后续建设的重要参考对象。根据现有照片，该平台至少包含以下功能入口：

- 项目登记与管理。
- 指标体系管理。
- 快速评价方法库。
- 标准及规范值查询。
- 标准及规范值管理。
- 项目运行状况。
- 待办任务列表。
- 按项目类型、负责人、评价年度、评价状态进行筛选。

后续平台访问恢复后，需要系统性梳理以下内容：

- 首页包含哪些区域。
- 项目列表有哪些字段。
- 项目状态如何定义。
- 待办任务如何生成。
- 每个项目点进去后有哪些页面。
- 一个项目从登记到评价完成经过哪些步骤。
- 指标体系如何维护。
- 方法库中有哪些评价方法。
- 标准规范值如何查询和引用。
- 成果报告如何生成或归档。

### 5.2 是否需要获取旧平台源码

建议争取获取旧平台源码，但目的不是直接复用旧代码，而是用于理解业务逻辑。

需要源码的理由：

- 可以快速搞清楚旧平台有哪些页面和流程。
- 可以看到项目、评价、指标、方法库、任务等模块之间如何关联。
- 可以提取旧系统字段、表结构、业务状态和流程节点。
- 可以减少靠截图猜测业务逻辑的时间。

但源码不是绝对必要条件。如果无法获取源码，也可以通过界面访问、截图记录、逐页梳理和接口抓包方式完成需求反推。

### 5.3 是否需要获取旧平台数据库

建议优先争取获取旧平台数据库结构，必要时再争取测试库账号。

数据库比源码更重要，因为它能直接反映业务对象和数据关系。

重点需要了解：

- 项目表。
- 区块表。
- 评价任务表。
- 指标体系表。
- 指标权重表。
- 标准规范值表。
- 评价结果表。
- 成果报告表。
- 用户角色表。
- 流程状态表。

如果无法获取真实数据库，也至少需要表结构说明或数据字典。

## 6. 数据建设计划

### 6.1 当前已经接入的数据类型

当前系统已经接入或初步接入的数据主要包括：

- 盆地数据：用于展示沉积盆地或含油气盆地的空间范围、名称、国家、面积、水深、分类等信息。
- 合同区块数据：用于展示勘探开发合同区块边界、合同名称、运营商、有效状态、面积、陆海属性等信息。
- 油气田数据：用于展示油气田空间范围、所属盆地、运营商、生产状态、油气类型、储量和发现开发信息。
- 井位数据：用于展示钻井位置、井名、井号、盆地、作业者、井型、总井深、完钻状态等信息。
- 井资料与曲线样例：用于展示井基础资料、井史事件、专题资料、测井曲线样例和采样表。
- 合同相关表格数据：用于展示合同及区块相关的业务属性。
- PDF 文档目录：用于后续建立报告资料、规范资料、项目档案和知识库。

### 6.2 当前数据接入方式

当前数据接入方式可以分为两类：

第一类是 GIS 空间数据：

- 原始数据多为 Shapefile。
- 通过 MapGIS IGServer 发布为 FeatureServer 服务。
- 前端通过接口请求 FeatureServer 的 query 接口。
- 返回空间几何和属性字段。
- 前端使用 Leaflet 在地图上绘制点、线、面。

第二类是表格和文档数据：

- 原始数据多为 Excel、CSV、PDF。
- 后端 Node.js 或脚本读取文件。
- 清洗并整理为 JSON 或可直接返回的 API 数据。
- 前端按业务模块展示为列表、详情、卡片、表格或摘要。

### 6.3 当前数据管理存在的问题

当前系统还没有建立正式数据库。现阶段更多是“文件目录 + 接口读取 + 前端展示”的方式。

这意味着：

- 数据没有统一入库。
- 数据之间的关联主要依靠名称、编号等字段匹配。
- 数据版本不容易管理。
- 数据质量无法系统性校验。
- 大数据量查询和筛选性能受限。
- 后续多人协作和权限控制会比较困难。

### 6.4 后续数据库建设计划

后续建议将数据库建设作为重点任务之一。

推荐方向：

- 使用 PostgreSQL + PostGIS 作为空间数据库底座。
- GIS 数据入库后由 PostGIS 管理几何、属性、索引和空间查询。
- Excel 表格数据清洗后入业务表。
- PDF 文件进入文档库，提取元数据进入数据库。
- MapGIS IGServer 可以继续作为 GIS 服务发布平台，从数据库或规范数据源发布服务。

初步数据库分层建议：

- 基础字典库：国家、地区、盆地、公司、资源类型、项目状态等。
- 空间图层库：盆地、区块、油气田、井位、管线、设施等。
- 业务属性库：合同、公司权益、储量、产量、井史、测试、分层、岩性等。
- 评价指标库：指标体系、权重、标准值、参数模板等。
- 评价结果库：项目评价记录、计算参数、结果、版本、报告等。
- 文档资料库：PDF、图件、报告、来源、标签、关联对象等。

## 7. 系统功能建设计划

### 7.1 首页工作台

首页应从当前的数据概览页面升级为业务工作台。

建议包含：

- 项目运行状况。
- 重点项目列表。
- 待办任务列表。
- 近期数据更新。
- 评价任务状态统计。
- 地图快捷入口。
- 常用方法库入口。

对标旧平台时，首页应保留“项目运行状况 + 待办任务”的核心逻辑。

### 7.2 数据资源中心

数据资源中心用于统一查看和管理所有数据。

建议包含：

- 空间数据目录。
- 表格数据目录。
- 文档资料目录。
- 数据来源说明。
- 数据更新时间。
- 数据质量状态。
- 数据字段说明。
- 数据关联关系。

现有“数据信息模块”可以演进为数据资源中心。

### 7.3 空间工作台

空间工作台是 GIS 数据展示和筛选的核心页面。

建议包含：

- 在线底图。
- 盆地图层。
- 区块图层。
- 油气田图层。
- 井位图层。
- 图层开关。
- 图例。
- 空间筛选。
- 属性查询。
- 快速定位。
- 框选查询。
- 图层加载诊断。

下一阶段重点要解决：

- 大数据量加载慢。
- 坐标偏差和投影统一。
- 不同图层样式混乱。
- 图层过密时可视化效果差。
- 地图操作卡顿。

### 7.4 项目登记与管理

这是旧平台中最值得借鉴的模块之一。

建议新增“项目管理”模块，支持：

- 新建评价项目。
- 选择项目类型。
- 选择所属国家、盆地、区块。
- 指定负责人。
- 指定评价年度。
- 设置项目状态。
- 关联基础数据。
- 查看项目进度。
- 归档评价成果。

项目状态可以初步设置为：

- 未开始。
- 资料收集中。
- 数据核查中。
- 评价计算中。
- 报告编制中。
- 已完成。
- 已归档。

### 7.5 指标体系管理

指标体系管理用于支撑评价算法。

建议包含：

- 指标分类。
- 指标名称。
- 指标含义。
- 指标单位。
- 指标权重。
- 评分区间。
- 标准值来源。
- 适用场景。
- 是否启用。

指标可按层级组织：

- 地质条件指标。
- 资源潜力指标。
- 勘探程度指标。
- 工程条件指标。
- 经济条件指标。
- 风险指标。

### 7.6 快速评价方法库

方法库用于管理评价算法和计算模板。

建议包含：

- 方法名称。
- 适用对象。
- 输入参数。
- 计算公式。
- 指标权重。
- 输出结果。
- 方法说明。
- 参考依据。
- 版本号。

优先建设的方法包括：

- 资源潜力评分法。
- 区块优选综合评分法。
- 风险加权评价法。
- EMV 期望货币价值法。
- 单位资源价值法。
- 市场类比法。

### 7.7 评价计算模块

评价算法模块应从当前结果展示型页面升级为参数输入型工具。

建议流程：

1. 选择评价对象。
2. 选择评价方法。
3. 自动读取已有数据。
4. 手工补充缺失参数。
5. 设置权重或采用默认权重。
6. 执行计算。
7. 展示指标得分。
8. 展示综合结果。
9. 输出计算说明。
10. 生成评价报告草稿。

该模块要特别强调“可解释”，不能只给一个分数。

### 7.8 标准及规范值查询

该模块对标旧平台“标准及规范值查询”和“标准及规范值管理”。

建议包含：

- 按专业查询标准值。
- 按指标查询标准值。
- 按地区或项目类型查询适用参数。
- 记录标准值来源。
- 支持标准值版本管理。
- 支持评价计算时调用标准值。

### 7.9 协同流程与待办任务

该模块用于体现“协同工作平台”的定位。

建议包含：

- 我的待办。
- 我负责的项目。
- 项目流转记录。
- 任务分派。
- 任务完成确认。
- 资料补充提醒。
- 评价状态更新。
- 操作日志。

短期可以先做静态或轻量版本，后续再接入真实用户权限。

### 7.10 成果报告模块

成果报告模块用于承接最终输出。

建议包含：

- 评价结果摘要。
- 关键指标表。
- 空间图件截图。
- 计算参数清单。
- 风险说明。
- 推荐结论。
- Word 或 PDF 报告导出。

## 8. 技术架构规划

### 8.1 当前技术架构

当前系统属于前后端结合的 Web 架构，但还不是严格意义上的成熟前后端分离业务系统。

当前主要组成：

- 前端：HTML、CSS、JavaScript、Leaflet、MapGIS Client for JavaScript 相关能力。
- 后端：Node.js 服务，负责静态页面访问、文件读取和 MapGIS 接口代理。
- GIS 服务：MapGIS IGServer，用于发布 Shapefile 为空间服务。
- 数据文件：Shapefile、Excel、CSV、PDF、JSON 等。
- 底图服务：天地图在线底图。

当前运行逻辑：

- 浏览器打开前端页面。
- 前端请求 Node.js 后端接口。
- Node.js 读取本地文件或代理 MapGIS IGServer。
- MapGIS IGServer 返回 GIS 图层要素。
- 前端 Leaflet 将返回的几何和属性绘制到地图上。

### 8.2 目标技术架构

后续建议演进为更清晰的三层架构：

- 前端展示层：负责页面、地图、筛选、交互、图表、报告预览。
- 后端业务层：负责接口、权限、数据清洗、评价计算、任务流转、日志监控。
- 数据与 GIS 服务层：负责数据库、空间数据库、MapGIS 服务、文件资料库。

目标架构建议：

- 前端：Vue 或继续使用原生 JS，但建议逐步模块化。
- 后端：Node.js 或 Python/FastAPI，可根据后续算法和数据处理需求选择。
- 数据库：PostgreSQL + PostGIS。
- GIS 服务：MapGIS IGServer。
- 文件服务：统一管理 Excel、PDF、图件和报告。
- 监控：接口耗时、服务状态、错误日志、请求量统计。

## 9. 性能与运行监测计划

### 9.1 当前性能问题

当前系统已经出现以下问题：

- MapGIS IGServer 大批量 FeatureServer 查询耗时较长。
- 一次性加载大量点、面要素会导致前端卡顿。
- 浏览器端绘制大量对象时性能下降。
- 用户不容易判断是前端慢、后端慢，还是 MapGIS 服务慢。
- 当前缺少系统化的日志、诊断和压力测试。

### 9.2 后续需要测试的内容

建议建立专项测试表，记录：

- 每个服务一次请求 100 条、500 条、1000 条、2000 条、5000 条的耗时。
- 每个图层总数据量。
- FeatureServer query 的最大稳定返回数量。
- 不同 outFields 数量对速度的影响。
- returnGeometry=true 与 false 的速度差异。
- 是否存在分页上限。
- MapGIS IGServer 内存占用情况。
- Node.js 代理耗时。
- 浏览器渲染耗时。

### 9.3 后续优化方向

推荐采用以下优化策略：

- 首屏只加载当前视野范围内的数据。
- 小比例尺下只显示聚合点或简化边界。
- 大比例尺下再显示详细井位和区块边界。
- 面图层优先使用简化几何。
- 点图层使用聚合或 Canvas 渲染。
- 使用分页请求，不一次性请求全部数据。
- 对常用查询结果做后端缓存。
- 对静态图层预生成轻量化 GeoJSON 或矢量切片。
- 对大规模正式数据使用 PostGIS 空间索引。
- 服务状态页面显示请求耗时、返回数量和错误信息。

## 13. 主要风险与应对措施

### 风险一：旧平台资料拿不到

应对：

- 通过界面截图和人工操作反推功能。
- 通过访谈业务人员补充流程。
- 先复刻核心流程，不依赖旧源码。

### 风险二：数据规模扩大后系统变慢

应对：

- 建立分页、视野范围加载、缓存和聚合策略。
- 建立性能测试和监控机制。
- 后续引入 PostGIS 空间索引。

### 风险三：评价算法缺少明确依据

应对：

- 先做方法调研和指标体系梳理。
- 与评价专家确认指标、权重和公式。
- 每个算法都保留公式说明、参数来源和适用条件。

### 风险四：数据标准不统一

应对：

- 建立统一编码规则。
- 建立字段映射表。
- 数据入库前做清洗和质量检查。

### 风险五：系统风格不符合业务方预期

应对：

- 参考旧平台的模块组织和业务流程。
- 采用更接近内部业务系统的页面结构。
- 减少演示性文字，增强表格、流程、任务、状态和报告能力。
